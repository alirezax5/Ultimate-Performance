# Installation

English | [فارسی](installation-fa.md)

This guide covers installing Ultimate Performance, identifying which serving mode
is active, configuring server acceleration on Nginx, verifying cache HITs,
purging the cache, and uninstalling.

## Requirements

| Component | Minimum | Recommended |
|---|---|---|
| WordPress | 6.0 | 6.7+ |
| PHP | 8.3 | 8.3+ (tested up to 8.5.4) |
| Web server (Server Accelerated) | Nginx 1.18+ | Nginx 1.28+ |
| Web server (PHP Fallback) | Any server running WordPress | — |
| Object cache backend (optional) | Redis 5+, Memcached 1.5+, APCu 5+, SQLite 3 (PDO), or writable filesystem | Redis |
| Multisite | supported (subdirectory + subdomain) | — |

PHP extensions required by the plugin itself: `pdo` (for the SQLite object
cache backend, if used), `redis` or `memcached` (only if you use that object
cache backend). The page cache has no PHP extension requirements beyond
WordPress itself.

## Install the ZIP

1. Download the latest release ZIP from the
   [Releases page](https://github.com/alirezax5/Ultimate-Performance/releases).
2. In `wp-admin → Plugins → Add New → Upload Plugin`, choose the ZIP and
   click **Install Now**.
3. Click **Activate**.

Or with WP-CLI:

```bash
wp plugin install ultimate-performance.zip --activate
```

## Activate the plugin

On activation, `UltimatePerformance\Core\Installer::activate()` runs. It:

1. Writes the default settings array (fail-closed; everything sensitive
   OFF by default except `php_fallback_enabled = true`).
2. Grants the `ultimate_performance_purge_all` capability to the
   `administrator` role.
3. Creates the cache root tree under
   `wp-content/cache/ultimate-performance/{v,meta,tmp}/`.
4. Writes a hardened `.htaccess` inside the cache root that denies every
   filename except `index.html` and blocks `.php`, `.json`, `.lock`,
   `.tmp`, dotfiles, and a list of dangerous extensions.
5. **Installs the `advanced-cache.php` drop-in** in
   `wp-content/advanced-cache.php` if `php_fallback_enabled` is `true`
   (the default) and no foreign drop-in already exists. The drop-in is
   generated by `AdvancedCacheDropin::generate_code()` and starts with
   `<?php` followed by the `OWNERSHIP_MARKER` comment.
6. Stores an environment snapshot (time + drop-in state) in the
   `uc_env_snapshot` transient.

## Identify the active mode

Open `Settings → Ultimate Performance`. The admin screen calls
`EnvironmentDetector::get_status_summary()` and shows one of:

| Mode label | Mode constant | Meaning |
|---|---|---|
| Server Accelerated | `SERVER_ACCELERATED` | Page cache configured; the web server is expected to serve cached bodies directly. Run the self-test probe to confirm. |
| PHP Compatibility | `PHP_FALLBACK` | The `advanced-cache.php` drop-in owned by UC is present and `WP_CACHE` is `true`. PHP fallback HITs are served by `FallbackServer::serve()`. |
| Misconfigured | `MISCONFIGURED` | The cache root is not writable, or the detected server is not in the supported list (Nginx / Apache / LiteSpeed / OLS). |
| Disabled | `DISABLED` | The plugin or the page cache is disabled in settings. |
| Conflicted | `CONFLICTED` | A foreign `advanced-cache.php` drop-in is present. UC will not overwrite it. |

The screen also shows the detected web server (`nginx`, `apache`,
`litespeed`, `ols`, `iis`, `unknown`) and a **Run self-test** button. The
self-test writes a probe cache entry, reads it back, and deletes it; a
passing self-test proves that the cache root is writable and readable.

## PHP Fallback setup (shared hosting, no root)

If `php_fallback_enabled = true` (the default) and no foreign
`advanced-cache.php` exists, the drop-in was already installed on plugin
activation. To activate it:

1. Open `wp-config.php` and ensure `define('WP_CACHE', true);` is
   present. WordPress loads `advanced-cache.php` only when this constant
   is `true`.
2. Save `wp-config.php`.
3. Verify the drop-in is owned by us: open
   `wp-content/advanced-cache.php`; the first 256 bytes must contain
   `/* Ultimate Performance advanced-cache.php v1 */`.
4. Verify `EnvironmentDetector` reports `PHP_FALLBACK`.

If a foreign drop-in exists (from another caching plugin), UC reports
`CONFLICTED` and will not install its own. Disable or remove the other
plugin's drop-in first, then deactivate and reactivate UC to install
ours.

## Nginx server acceleration setup

The recommended way to enable Nginx direct-serve is to **modify your existing per-site vhost** (e.g. `/etc/nginx/conf.d/<site>.conf` or `/www/server/panel/vhost/nginx/<site>.conf`) by adding cache-aware rules to the existing `server {}` block. **Do NOT modify the main `nginx.conf`** — only the per-site vhost.

### Quick setup

1. In `Settings → Ultimate Performance → Server Integration`, fill in the **Nginx integration** inputs:
   - **Origin** — IP:port of the PHP origin (e.g. `127.0.0.1:8080`).
   - **Listen** — IP:port Nginx should listen on (e.g. `127.0.0.1:8097`).
   Save settings. The plugin validates both as `IP:port` literals
   (max 21 chars, fail-closed on anything else).

2. In your per-site vhost, add the following rules INSIDE the existing `server {}` block (typically right before the `location /` block). See `examples/nginx.sample.conf` in the plugin directory for a complete reference.

   ```nginx
   # Skip-cache flag — set to 1 if request is dynamic (logged-in, cart, etc.)
   set $up_skip_cache 0;

   if ($request_method = POST) { set $up_skip_cache 1; }
   if ($http_cookie ~* "wordpress_logged_in_|comment_author_|wp-postpass_|woocommerce_items_in_cart|woocommerce_cart_hash|wp_woocommerce_session_|wordpress_sec_") { set $up_skip_cache 1; }
   if ($request_uri ~* "/wp-admin/|/wp-login\.php|/wp-cron\.php|/xmlrpc\.php|/wp-json/|/cart/|/checkout/|/my-account/|/wc-api/|/wc-ajax/") { set $up_skip_cache 1; }
   if ($is_args) { set $up_skip_cache 1; }

   # Conditional rewrite — sends cacheable requests to /up-cache/
   if ($up_skip_cache = 0) {
       rewrite ^/(.+)/$ /up-cache/<SITE_HOST>/$1/index.html last;
       rewrite ^ /up-cache/<SITE_HOST>/uc-root/index.html last;
   }

   # Internal-only cache serving location
   location ^~ /up-cache/ {
       internal;
       alias <CACHE_ROOT>/v/;
       default_type text/html;
       add_header X-Ultimate-Performance "HIT" always;
       add_header X-Cache-Status "HIT" always;
       add_header Cache-Control "public, max-age=3600";
       expires 1h;
       try_files $uri /index.php?$args;
   }

   # Security: deny direct access to cache metadata files
   location ~* /wp-content/cache/ultimate-performance/(meta|tmp|genlocks|stats|\.htaccess) {
       deny all;
       return 404;
   }
   ```

   Replace `<SITE_HOST>` (e.g. `example.com`) and `<CACHE_ROOT>` (e.g. `/var/www/example.com/wp-content/cache/ultimate-performance`) with your own values.

3. Test the config: `sudo nginx -t`
4. Reload Nginx: `sudo nginx -s reload`
5. In the admin screen, click **Verify Nginx rules** button. The verify probe writes a file at `/uc-verify-<token>/` with a byte-identical body, then issues an HTTP request. If the response body matches `probe_body($token)` exactly, the snippet is serving statically — Server Accelerated mode is active.

### Why use `rewrite ... last` instead of `try_files $up_cache_file`?

Nginx's `try_files` looks for the file **inside `$document_root`**. The cache files live at `<DOCROOT>/wp-content/cache/ultimate-performance/v/<host>/<path>/index.html` — which IS inside `$document_root`. So one might be tempted to use:

```nginx
try_files /wp-content/cache/ultimate-performance/v/<host>${uri}index.html $uri $uri/ /index.php?$args;
```

This works, but exposes the cache path in nginx error logs and doesn't let you add the `X-Ultimate-Performance: HIT` header.

The `rewrite ... last` approach redirects cacheable requests to the internal `location ^~ /up-cache/` which uses `alias` to map `/up-cache/` to the cache directory. This:
- Hides the cache path from error logs
- Lets you add response headers (X-Ultimate-Performance, Cache-Control)
- Lets you handle the cache MISS fallback (try_files in /up-cache/ falls through to /index.php)
- Lets you serve the cached file with custom headers

### Important note about `if` in nginx

Nginx's `if` directive is famously called ["if is evil"](https://www.nginx.com/resources/wiki/start/topics/depth/ifisevil/). The key gotcha:

- `if` blocks at the **server scope** (outside `location`) are evaluated during the **rewrite phase**, BEFORE location matching. This is what we use above — the `set $up_skip_cache 1` happens before the `rewrite` decision.
- `if` blocks INSIDE a `location {}` block are evaluated AFTER the location is matched. This means a `if ($up_skip_cache = 0) { rewrite ... }` inside `location /` does NOT work as expected — the variable was already evaluated.

That's why our `if` checks live at server scope (in the extension file or in the vhost itself before `location /`), not inside `location /`.

### Skip-cache cookies

The regex `wordpress_logged_in_|comment_author_|wp-postpass_|woocommerce_items_in_cart|woocommerce_cart_hash|wp_woocommerce_session_|wordpress_sec_` matches the cookie NAME patterns WordPress and WooCommerce use. Specifically:

- `wordpress_logged_in_<32-hex>` — set when a user logs in
- `wordpress_sec_<32-hex>` — security cookie for logged-in users
- `comment_author_<32-hex>` — set when a visitor comments
- `wp-postpass` — set when a visitor enters a post password
- `woocommerce_items_in_cart` — set when a cart has items
- `woocommerce_cart_hash` — set when cart contents change
- `wp_woocommerce_session_<id>` — WooCommerce customer session

When ANY of these cookies is present in the request, `$up_skip_cache` is set to 1 and the request bypasses the cache rewrite, falling through to PHP-FPM.

## Verify caching works

### Verify a MISS (first request)

```bash
curl -I https://example.com/
```

Expected response header (Server Accelerated or PHP Fallback):

```
X-Ultimate-Performance: MISS
```

(On Server Accelerated mode the header is emitted by `Engine` on the
MISS write path; subsequent HITs are served by Nginx with no PHP-level
header.)

### Verify a FALLBACK-HIT (PHP fallback mode)

```bash
curl -s -o /dev/null -D - https://example.com/ | grep -i 'x-ultimate-performance'
```

Expected:

```
X-Ultimate-Performance: FALLBACK-HIT
```

`FallbackServer::serve()` emits this header before exiting; the body
comes straight from `v/<host>/<path>/index.html`.

### Verify a server HIT (Server Accelerated mode)

Server-accelerated HITs do not run PHP, so the `X-Ultimate-Performance: HIT`
header is **not** present. Two ways to verify:

1. **TTFB measurement:** a server HIT completes in ~0.3 ms TTFB (file
   read + Nginx overhead); a MISS takes 40–400 ms (full WordPress
   render). Use `curl -w "@-" -o /dev/null -s https://example.com/ <<<'%{time_starttransfer}\n'`.
2. **Cache file inspection:** after the first request, look for
   `wp-content/cache/ultimate-performance/v/<host>/uc-root/index.html`. If
   the file exists and the second request is significantly faster, the
   server is serving from disk.

The admin self-test probe is the simplest end-to-end proof.

## Purge the cache

- **Purge single URL:** in the admin screen, enter the URL in the
  **Purge URL** field and click **Purge**. This calls
  `Hooks::purge_url()`, which tries both `https://` and `http://`
  variants and removes the cached body + meta + tag-registry entries.
- **Purge all:** click **Purge entire cache** (double-confirmation;
  requires the `ultimate_performance_purge_all` capability). Calls
  `Hooks::purge_site()`, which deletes the whole `v/` tree, the `meta/`
  tree, and queues an LSCache purge-all (if LiteSpeed is in use). Node
  identity (`meta/node-id.json`) is preserved across a purge-all.
- **WP-CLI:** for cluster-scoped actions:
  ```bash
  wp ultimate-performance cluster status
  wp ultimate-performance cluster epoch --bump       # forces every node to reconcile
  wp ultimate-performance cluster events
  wp ultimate-performance cluster reconcile          # local node only
  ```

Content edits (`save_post`, `delete_post`, `edit_term`,
`woocommerce_update_product`, `transition_comment_status`, etc.) purge
the affected objects **synchronously** for the edited permalink and
**asynchronously** for the broader tag fanout.

## Uninstall

1. In `wp-admin → Plugins`, deactivate Ultimate Performance. On deactivation:
   - WP-Cron hooks (`ultimate_performance_tick`, `ultimate_performance_janitor`)
     are cleared.
   - If we own `wp-content/object-cache.php`, it is removed.
   - If we own `wp-content/advanced-cache.php`, it is removed.
2. Click **Delete**. WordPress defines `WP_UNINSTALL_PLUGIN` and runs
   `uninstall.php`, which calls `Installer::uninstall_data()`. This:
   - Resets the `ultimate_performance_settings` option to defaults.
   - Deletes every plugin-owned transient
     (`uc_env_snapshot`, `uc_oc_dropin_status`, `uc_registry_overflow`,
     `uc_settings_errors`).
   - Clears all plugin cron hooks.
   - Removes the `ultimate_performance_purge_all` capability from
     `administrator`.
   - Drops the three shared cluster tables
     (`uc_invalidation_events`, `uc_cluster_epoch`,
     `uc_cluster_nodes`) on the base prefix — one DROP for the whole
     multisite network.
   - Recursively removes the entire cache tree at
     `wp-content/cache/ultimate-performance/`.
3. **Never performed** (release-blocking honesty contract):
   - No `FLUSHALL` / `FLUSHDB` on Redis.
   - No `flush_all` on Memcached.
   - No `apcu_clear_cache()` on APCu.

   A foreign Redis / Memcached / APCu key survives every uninstall.
